案例 02

DataTalk

角色个人 0-1 项目 时间2026.06 – 2026.08 领域AI + 商业智能（Chat BI）

让不会写 SQL 的运营，用一句话拿到数。难的不是"能不能问"，是"问出来的数，能不能信"。

01问题

增长、渠道、内容运营人员不会写 SQL——取数要么等一张固定报表，要么排队等技术团队写查询，门槛高、链路长。

但这个产品真正要解决的不是"能不能问数"，而是问出来的数准不准。一个查得很快、但结果错的问数产品，比没有更危险。

02关键判断
  • 先解决"模型看到什么"：不把几百个字段一次性塞给模型，而是用字段级检索 + Schema 关系图，只给它当下需要的那张子图。
  • 权限做在检索层：按角色加载可用数据表，权限贯穿检索、建图、SQL、工具四个环节——不是只在下游拦一道。
  • 承认歧义：业务口径有歧义时，宁可让产品发起澄清，也不让模型猜一个看起来合理的答案。
03系统架构

我把这条问数链路，用 LangGraph 编成了一张可分支、可中断、可恢复的图——而不是一问一答的直线。

  • 工作流：请求先进预处理判定意图，再分三条路——闲聊直接答、基于已有结果做分析、或去查数据库。查库这条会经过"检索 Schema →（必要时）向人澄清 → 生成并执行 SQL"。用图来编排的关键收益是：澄清能中断流程、等用户回答后再恢复，这条能力直线链条给不了。
  • 给模型看什么：不把几百个字段全塞进去，而是字段级检索 + Schema 关系图，只喂它当下需要的子图——这是挡幻觉的第一道闸。
  • 权限：每个请求带一个访问范围，工具按角色注册——没权限的用户根本看不到对应的数据库工具；SQL 执行时再二次校验（只读、单语句、禁 SELECT *）。
  • 把规则沉淀成 Skill："怎么写对一条 SQL"（粒度、口径、时间规则、返回列顺序）写成一份 SKILL.md，而不是塞进系统提示词——规则可版本化、可独立迭代。
  • 查询契约：模型执行前必须先声明一份 query_contract（粒度 / 来源表 / 条件 / 指标 / 返回列），让"它到底想查什么"变得可核对。
MCP 工具每个数据库一个只读查询工具（query_数据库名），外加当前时间、解析相对日期、生成柱状图、生成饼图四个辅助工具。关键在注册方式：工具按角色注册——没权限的库，模型连工具都看不到，而不是"看到了再被拒绝"。
Skill ×2database_query（怎么把一句话写成一条对的只读 SQL）与 data_qa（基于已有结果做分析、出报告）。规则写进 SKILL.md——可版本化、可独立迭代，不污染主提示词。

04取舍

我的评测做了两个明确的取舍，而且我把它们写在了明面上：

  • 评的是"检索对了之后"：评测给定标准的检索词，所以我测的是"检索正确后，模型能不能把 SQL 写对"，不是端到端。先把能控的部分测准，端到端留到下一版。
  • 澄清没能纳入评测：澄清机制我设计了，但 430 条用例基本都给了明确查询，澄清实际 0 次触发。这是我这套评测的一个盲区，我没有藏它。
05验证

我建了一套 430 条用例的评测集，覆盖增长、渠道、内容三类运营场景，从"字段召回 → SQL 执行 → 结果正确"一路量化到底。

再往下拆一层：简单查询正确率 86.6%，复杂查询只有 33.3%——问题集中爆发在多表关联与聚合逻辑上。这就是这套评测最值钱的产出：它没有给我一个高分，给我的是一个"该先修哪里"的答案。

06下一步
  • 修多表关联与聚合：复杂查询只有 33%，这是最该先动的地方。
  • 把"澄清"纳入评测：补一组"模糊意图"用例，让端到端链路真正被测到。
  • 建口径层（指标字典）：现在 Schema 精确率只有 19.44%——召回太宽。缺的正是一个统一的指标口径层，让"新增用户"这类词在不同角色下指向同一个定义。
