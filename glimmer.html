案例 01

Glimmer 智能体

角色个人 0-1 项目 时间2026.03 – 2026.06 领域AI + 校园心理陪伴

它最难的不是"聊得像人"，而是——当一个人真的处在高风险里时，怎么保证它一定接得住。

01问题

目标用户是那些不敢求助、也不知道该找谁的学生。这个场景有一条硬边界：AI 不能替代心理咨询师。而一旦漏掉一个真正处在高风险里的人，代价无法接受。

所以我把产品的核心，从"能不能陪聊"拉回到一个更硬的问题：怎么把风险接住，并且说清楚 AI 和人工各自的边界在哪。

02关键判断
  • 分层响应：把对话分成 CHAT / CONSULT / RISK 三层，普通聊天不强行做心理测评——既控制成本，也避免对正常人过度干预。
  • 三级风险判定：词典硬信号 → 模型结构化评估 → 启发式兜底；并设一个独立的 Safety Agent，对高风险回复拥有一票否决权。
  • 处置不是终点：高风险不进"黑名单"，而是进一条责任链——风险报告 → 个案创建 → 辅导员预警 → 人工确认。
03系统架构

我把系统拆成四层，每层只解决一个问题——这样任何一层出问题，都不会让整条对话垮掉。

  • 编排层 · 多 Agent：理解、风险评估、上下文、回复各由一个专业 Agent 负责，再由协调 Agent 收敛。我坚持让风险判定独立于对话生成——如果让模型"一边聊天一边自己判断安不安全"，它很容易为了把话说圆而放过风险。
  • 安全层 · 三层兜底：词典硬信号（命中即高危，不依赖模型）→ 模型结构化评估 → 启发式兜底（模型挂了也不崩）。Safety Agent 还会对候选回复一票否决：高风险回复缺安全指引，直接打回重写。
  • 检索层 · 动态路由：普通闲聊不查知识库（省成本、更快），只有求助与风险才走"向量 + BM25 + 重排"的混合检索；向量服务不可用时自动降级为纯关键词，对话不中断。
  • 处置层 · 异步责任链：高风险不进"黑名单"，而进一条后台责任链——写台账、建个案、推预警，幂等、可重试、有死信，且不阻塞学生端的流式回复。
MCP 工具6 个——写台账、建个案、发预警、确认个案、追加备注、发预警邮件。我把"处置链"的每个动作标准化成工具，而不是写死在流程里：Agent 只决定"要不要处置"，工具负责"怎么处置"。
Skill7 个场景技能——学业压力、焦虑安抚、睡眠作息、高危安全计划、转介资源、转介摘要、基础支持。按场景加载，给回复加领域约束；写成 SKILL.md，规则可版本化、可单独评审。
Harness两层——一层跑业务（GlimmerAgentHarness），一层做验证（6 套回归：风险 / 路由 / 技能 / RAG / API / 工具队列）。验证层用 mock 模型 + 临时 SQLite + 内存记忆，不依赖真实 MySQL / Redis / 模型，随时全链路自检。产品"怎么跑"和"怎么证明它没坏"是两件事。

04取舍

我想提高高风险召回，通常只有两条路：放宽判定阈值，或者改模型。我先试了改 Prompt。

结果召回从 83.3% 抬到了 87.5%，但误报率从 2.1% 猛涨到 8.3%——新增的误报几乎全是"玩梗"的正常学生。这让我判断：光靠 Prompt"宁可高估"会误伤玩笑，正解是把玩笑、黑话的降权落到规则层。

于是我放弃了这条捷径，保留原方案。宁可承认"一次没解决"，也不上线一个会吓到正常人的版本。

05验证

我用一套 96 例的安全评测集来量化"接不接得住"——48 条高风险样本 + 48 条正常样本，覆盖隐喻、黑话、躯体化、玩笑、否认等最难的类型。

83.3%高风险召回（真模型）
2.1%误报率
33.3%纯规则基线召回 · 模型层带来 50pt 增量

这组数字里，真正说明问题的是那个 33.3%：如果只靠关键词硬匹配，十个人里只能接住三个。是模型层的评估，把它抬到了 83%。

06下一步
  • 落地规则层降权：把"玩梗 / 黑话 + 无明确危险信号"标记出来降权，再跑一轮 SafetyEval 对比，把误报打回去、同时保住召回。
  • 评测集扩容：安全集 96 → 120，回复集 60 → 100+，尽量掺入真实会话日志。
  • 补真实标注一致性：现有 kappa 0.886 是"人 vs LLM 代理"，要找真人做双标。
